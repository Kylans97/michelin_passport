# Applying the 2026-11-01 catalogue work to production

Prepared on branch `claude/lucid-rubin-us4we5` (head `4c6f24d` or later). Run
it from a machine with the Supabase CLI linked to production.

Every prepared SQL file is **one transaction with its own checks**. On any
problem it raises, rolls back and changes nothing.

## 0. Get a checkout that has main's migrations too

This branch is behind `main` by 137 commits. `supabase db push` refuses to
run when the remote ledger holds migrations that the local folder lacks, so
do **not** apply from the bare branch. Make a local apply branch instead:

```bash
git fetch origin
git checkout -b apply-2026-11-01 origin/main
git merge --no-ff origin/claude/lucid-rubin-us4we5
```

- **Conflicts:** resolve any in `supabase/data/qa_issues.csv` by keeping both
  sides' rows. The branch adds QA-392 to QA-403; main ends at QA-391. If main
  has meanwhile taken any of those numbers, stop and report.
- **Pushing:** do not push this apply branch to `main`. Merging to main is the
  product owner's call.

Then check the migration order:

```bash
ls supabase/migrations | tail -3
```

The last two must be `20261031160000_add_pt_2026_star_cities.sql` and
`20261031170000_add_pt_key_hotel_cities.sql`. If main now has a migration
numbered higher than 20261031160000, **stop and report**. Both files then
need renaming to follow it, which is allowed because neither has been
applied.

```bash

supabase db query --linked --file michelin_keys_pt_2026/prepared_pt_key_hotels_2026.sql
supabase db query --linked --file michelin_pt_stars/prepared_pt_stars_2026.sql

for f in europe_gaps/prepared_*_gap_fill.sql; do
  echo "== $f"
  supabase db query --linked --file "$f" || break

supabase db query --linked --file europe_gaps/prepared_location_corrections.sql
```

| File | Effect |
|---|---|
| PT Key hotels | 69 hotels `hotel_2810`–`hotel_2878`, Keys 2/14/53, with 65 Place IDs, 64 phones and 65 websites |
| PT stars 2026 | 52 restaurants `rest_3761`–`rest_3812`, 16 Key-hotel links and 4 `property_name`. Portugal becomes MICHELIN's live 2026 listing. |
| CH/AT/Nordics | Fill-only, from 256 rows: 250 Place IDs, 13 phones, 1 website, 1 `property_name`. No star changes. |
| 27 Europe gap files | Fill-only, from 1,873 rows: 1,606 Place IDs, 347 phones, 831 websites |
| Location corrections | 18 rows (coordinates, each guarded on the old point within 5 m) and 12 Place IDs |

**The order matters in three places:**

- The PT stars file needs both migrations and the PT hotels file. It links
  restaurants to those hotels.
- The PT hotels file needs migration 20261031170000.
- The location corrections go last.

The CH/AT/Nordics file and the gap files no longer overlap on any
conflicting value (fixed 2026-11-01), so between those two the order does
not matter.

### When a file aborts

The error names the check, for example "code is no longer the exported row",
"Place ID already used by another row", or "expected N … found M".

- Nothing from that file was applied. **Do not edit the file and retry.**
- Note the file and the error, carry on with the files that do not depend on
  it, and report at the end.

An abort usually means production changed after the export (2026-10-31 and
2026-11-01). That needs a fresh export, not a workaround.

**Re-runs:** the fill-only files (the CH/AT/Nordics file and the gap files)
are harmless to run twice. The PT files and the location corrections abort
on a second run, which is by design.
